## Multi-Stage Dockerfile

The image builds from `app/dashboard/Dockerfile` using the **monorepo root as the build context**, so manifest, source, and entrypoint paths are repo-relative:

```dockerfile
# Stage 0 (base): Bun 1.3.14 + pnpm, runtime tooling, non-root appuser (1000:1000)
# Stage 1 (builder): pnpm install --filter @abugida/dashboard --frozen-lockfile,
#                    then the TanStack Start production build (vite build)
# Stage 2 (runtime): pruned production node_modules + dist/ + Bun SSR server
CMD ["bun", "server.mjs"]
```

The workspace layout is preserved in the runtime image so pnpm symlinks into the root virtual store resolve. The container runs as a non-root user (`appuser`, uid/gid 1000), and a dependency-wait entrypoint execs the server as PID 1 after all declared dependencies are healthy.

## Dependencies

| Service                  | Connection        | Purpose                                                       |
| ------------------------ | ----------------- | ------------------------------------------------------------- |
| PgBouncer (`:6432`)      | Pooled PostgreSQL | Application data, user records, dashboard state (per ADR-019) |
| Redis (`:6379`)          | Direct            | Session storage, caching                                      |
| OTEL Collector (`:4317`) | gRPC              | Metrics, traces, and logs export                              |

Both data-layer dependencies use `condition: service_healthy`, ensuring the Dashboard only starts after PgBouncer and Redis are confirmed operational.

All application services connect to PostgreSQL **through PgBouncer** (per ADR-019). The former direct-connection exception for this service ([ADR-013](../architecture/adr/)) is superseded and no longer applies.

## Environment Variables

| Variable                            | Purpose                                                   |
| ----------------------------------- | --------------------------------------------------------- |
| `PGBOUNCER_HOST` / `PGBOUNCER_PORT` | PgBouncer address for pooled DB connections (per ADR-019) |
| `REDIS_HOST` / `REDIS_PORT`         | Redis primary address for session/cache operations        |
| `OTEL_EXPORTER_OTLP_ENDPOINT`       | OTel Collector (`otel-collector:4317`)                    |
| `DEPLOY_VERSION`                    | Deployment version label for observability filtering      |

Secrets (`POSTGRES_PASSWORD`, `REDIS_PASSWORD`) are injected as environment variables — from `.env` in development, exported from Vault in staging/production (ADR-006).

## Health Check

The service exposes a `/health` endpoint confirming the Bun server is accepting connections. Docker probes it via `curl -sf http://localhost:8080/health`; Compose uses the same check for dependency resolution.

---

## Deployment Topology

| Environment | Replicas                    | Port Exposure                         | Ingress                      |
| ----------- | --------------------------- | ------------------------------------- | ---------------------------- |
| Staging     | `DASHBOARD_REPLICAS`        | `${DASHBOARD_PORT:-8081}:8080` (host) | Direct access for validation |
| Prod        | Scaled via replica settings | None published                        | Via Caddy                    |

Container names are auto-generated by Compose (`infra-dashboard-1` style) rather than fixed names, so upstream discovery relies on Compose service DNS (`dashboard:8080`). Traffic shifting follows the same blue-green and canary patterns as the API service.
